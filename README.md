# Лавка — MVP учёта магазина

Рабочие сценарии: товары (создание, изменение, архив), партии закупок, продажи FIFO с распределением по партиям, расходы и категории, повтор постоянного расхода, взвешивание, первичная инвентаризация, история, текущие остатки, месячный отчёт, настройки.

## Технологии и отклонения от рекомендованного стека

TypeScript, React, Next.js App Router API на Vinext, Tailwind CSS, Lucide. Для размещения Sites используются Cloudflare Workers + D1 + Drizzle вместо PostgreSQL + Prisma. Доступ через вход Sites/ChatGPT, без собственной регистрации email/пароль. Данные разделены по идентификатору пользователя; новая публикация приватная.

Деньги хранятся целыми копейками, количество — тысячными долями единицы. Для штучного товара разрешены только целые единицы. Умножение и округление выполняются BigInt. Клиентский предварительный расчёт не используется для записи: сервер пересчитывает все значения.

## Запуск

Требуется Node.js 22.13+ (для встроенного запуска тестов TypeScript рекомендуется Node.js 24).

```powershell
npm ci
npm run db:generate
npm run build
npx wrangler d1 execute DB --local --persist-to .wrangler/state --config dist/server/wrangler.json --file drizzle/0000_careless_ultimates.sql
npm run dev
```

Локальный адрес: http://127.0.0.1:5173. Локальный вход в тестовую учётную запись предоставляется только сервером разработки. Производственная база создаётся и мигрирует при публикации Sites. Локальные тестовые данные туда не переносятся.

В ограниченной Windows-среде npm.cmd может некорректно разрешать путь. Проверенный обход: `node "C:/Program Files/nodejs/node_modules/npm/bin/npm-cli.js" run install:ci`. Если Drizzle сообщает `uv_os_get_passwd ENOMEM`, это ограничение окружения, а не ошибка схемы; используйте обычный терминал Windows.

## Проверки

```powershell
node --test tests/ledger.test.mjs
node --test tests/api.test.mjs
npx tsc --noEmit
npx eslint app lib db
npm run build
```

API-тест запускается только с работающим локальным сервером и мигрированной локальной базой. Создаёт помеченные тестовые записи, не очищает чужие данные. Проверяет авторизацию, Origin, FIFO, конкурентные продажи, взвешивание, расходы, запрет повторного расхода, архив.

Подтверждено: 14 модульных тестов; интеграционный сценарий; TypeScript; ESLint; сборка; создание товара и закупки через UI; обзор и таблица на 390 px.

## Правила и ограничения

### Оборачиваемость и подготовка дозаказа

- API возвращает `analytics`: товары и товарные группы. В серверном режиме расчёт выполняется сервером; автономная версия использует ту же функцию `inventoryAnalytics`.
- Средняя оборачиваемость: `Σ(себестоимость распределения FIFO × дни от закупки до продажи) / Σ(себестоимость распределений)`. Выбираются продажи за период отчёта, до сегодняшней даты. Это срок хранения проданного капитала, не срок получения оплаты: модель не содержит платежей/дебиторской задолженности.
- Средняя наценка: `(выручка продаж − себестоимость продаж) / себестоимость продаж × 100%`. Используются реальные цены продаж и закупок FIFO; текущая цена карточки не заменяет историю. Группы суммируют базовые величины, а не усредняют проценты товаров.
- Стоимость текущего остатка: сумма стоимости оставшегося количества каждой партии. Залежавшийся товар: хотя бы одна известная закупочная партия с ненулевым остатком старше `settings.staleDays`. Неизвестный возраст без старых известных партий даёт «Недостаточно данных». Излишки инвентаризации не получают фиктивную дату закупки.
- При отсутствии продаж или нулевой себестоимости соответствующие показатели равны `null`. Если хотя бы одно распределение продаж не имеет известной даты закупки, оборачиваемость равна `null`; интерфейс показывает «Недостаточно данных». Неизвестная дата не мешает расчёту фактической наценки.
- Поле товара `replenishment` хранит основного поставщика и `leadTimeDays` (0–365 либо `null`); существующие JSON-записи совместимы, миграция D1 не требуется. Средняя скорость продаж — количество за последние до 30 календарных дней с первой записи остатка / число этих дней; дни без продаж включены. Количество возвращается в тысячных долях единицы в день; группы с разными единицами не суммируются.
- `reorderPointQuantity` и `recommendedOrderQuantity` подготовлены в контракте аналитики как `null`. Их расчёт, страховой запас, сезонность и создание заказа относятся к следующему этапу.
- Проверка изменения: 26 модульных тестов PASS, TypeScript PASS, ESLint PASS, серверная сборка PASS; таблица товаров, карточка и группы проверены в браузере автономной версии. Интеграционный API-тест расширен, но запуск заблокирован локальной ошибкой Cloudflare/Miniflare `spawn UNKNOWN`; повторить `node --test tests/api.test.mjs` после запуска локального сервера.

- FIFO упорядочен по дате операции, времени создания и ID. Ввод задним числом пересчитывает историю; операция, создающая дефицит в прошлом, отклоняется.
- Операции D1 записываются одним атомарным batch. Проверка версии магазина внутри транзакции предотвращает конкурентную перезапись. При конфликте нужно обновить данные.
- Округление стоимости списания через разницу стоимости остатка сохраняет общую стоимость партии до копейки.
- Корректировки вниз списывают FIFO; излишек создаёт отдельную партию по введённой цене. Взвешивание фиксируется сегодняшним днём.
- Чистый результат строго соответствует формуле ТЗ: выручка − себестоимость продаж − расходы. Потери от корректировок показаны отдельно и не вычтены повторно.
- Первичная инвентаризация не считается закупкой месяца. Неизвестная дата помечается и исключается из возраста, для порядка FIFO используется дата ввода.
- При архивировании остаток должен быть нулевым. История сохраняется. Продажи и закупки неизменяемы; удаление расхода требует подтверждения.
- Демо — отдельный несохраняемый пример, доступный для просмотра. Реальный магазин начинает с нулей.
- Модель хранения: отдельные таблицы сущностей с JSON-полями, составным ключом владелец/ID и серверной валидацией. Настройки находятся в записи владельца. Это не полная нормализованная Prisma-схема из ТЗ.
- Для небольшого магазина все операции одного владельца читаются и пересчитываются целиком. До большого объёма истории нужны пагинация, индексированные поля и нагрузочное тестирование. Резервное копирование/восстановление через UI не входит в эту сборку.

## Оценка реализации

8/10 | Code 8 | Arch 7 | Perf 6 | Security 8 | UI/UX 8 | Testability 8

Solid: серверные расчёты, целые деньги, атомарная проверка версии, реконструкция остатков на конец месяца.
Weak: db/store.ts и lib/ledger.ts — чтение и пересчёт полной истории; JSON-поля вместо нормализованных колонок.
FIFO, конкуренция, валидация, локальный UI → PASS.
Основной риск: производительность при большой истории и отсутствие проверки восстановления резервной копии.
Следующий шаг: прогон на реальном объёме магазина и проверка восстановления данных перед боевым использованием.

## Дизайн

Основа: bundled Refero typography.md — один нейтральный шрифт, табличные цифры и три уровня иерархии. craft-details.md — подписи форм, нативный dialog, фокус, семантическая навигация и состояния сохранения.
Фиксированное направление: белые поверхности на прохладном сером фоне, зелёный для основного действия/положительного результата; тёмная карточка «Сейчас в товаре» — главный акцент по ТЗ. Янтарный — только старые партии/проверки. Иллюстрации не используются в рабочей поверхности.
